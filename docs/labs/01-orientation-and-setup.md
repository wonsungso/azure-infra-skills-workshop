# Lab 01: 워크샵 시작하기 — 역할 이해와 환경 준비

⏱ **예상 시간:** 30분
🎯 **이 랩에서 배우는 것**
- Azure Skill, MCP 도구, 사람의 역할이 어떻게 나뉘는지
- 우리 팀만의 입력값(구독, 리전, 이름 등)을 어디에 어떻게 기록하는지
- 배정된 Azure 범위가 실제로 맞는지 "읽기 전용"으로 확인하는 방법

🟦⬜⬜⬜⬜⬜⬜⬜ **Lab 1 / 8** · 🧭 1부 설계와 검증 · 🏆 획득 배지 `환경 탐색가`

> 🎬 **미션 진행 상황**
> 팀장의 요청을 방금 받았습니다. 아직 아무것도 만들지 않았죠. 서두르기 전에, **내가 무엇을 건드릴 수 있는 사람인지**부터 확인합니다.

## 왜 이 랩이 필요한가요?

이 워크샵은 AKS 명령어를 외우는 자리가 아닙니다. Azure Skill(`azure-enterprise-infra-planner`, `azure-kubernetes` 등)에게 "이 작업을 해줘"라고 요청하면, Skill은 판단 기준과 절차를 알고 있고 실제 실행은 MCP 도구나 CLI가 담당합니다. 하지만 **무엇을 승인할지, 결과가 진짜인지 확인하는 것은 항상 사람의 몫**입니다. 이 랩에서는 그 역할 분담을 먼저 이해하고, 이후 모든 프롬프트가 공유할 입력값을 확정한 뒤, 우리 팀에게 배정된 Azure 범위가 실제로 존재하는지 확인합니다.

## 시작 전에 확인하세요

- [README](../../README.md)와 [설계 결정](../00-design-decisions.md)을 한 번 읽었나요?
- [사전 준비](../01-prerequisites.md)의 참가자 항목을 마쳤나요?

## Step 1. 역할과 안전 규칙 이해하기 (5분)

다음 세 가지 역할을 기억하세요.

| 역할 | 하는 일 | 예시 |
| --- | --- | --- |
| Azure Skill | 절차, 모범 사례, 위험 판단 기준 제공 | "이 CIDR은 다른 서브넷과 겹칩니다" |
| MCP 도구 / CLI | 실제 조회·생성·배포 실행 | `az aks show`, Bicep validate |
| 참가자(사람) | 대상 범위 확인, 승인, 결과 검증 | "이 리소스 그룹이 맞다", "배포를 승인한다" |

이 워크샵에서 항상 지키는 규칙입니다.

- Skill 이름을 프롬프트에 썼다고 해서 실제로 실행됐다는 뜻이 아닙니다. 응답에서 어떤 Skill 지침을 참고했는지, 어떤 도구를 실제로 호출했는지 확인하세요.
- 리소스를 만들거나 바꾸거나 지우기 전에는 항상 사람이 승인합니다.
- 예상되는 결과와 실제로 확인한 결과는 항상 구분해서 기록합니다(`예상` vs `관측`).

> [!TIP]
> 헷갈리면 "지금 이 작업이 실제로 Azure를 바꾸는 건가요, 아니면 읽기만 하는 건가요?"를 에이전트에게 먼저 물어보세요.

## Step 2. 내 공통 입력값 정하기 (10분)

[공통 입력표](../../templates/team-inputs.md)를 엽니다. 이 워크샵에는 값을 대신 알려주는 사람이 없으므로, **직접 조사해서** 채웁니다.

지금 채울 수 있는 것부터 시작하세요.

- **구독, 리소스 그룹, 클러스터 base 이름**: 내가 쓸 값을 정합니다. 리소스 그룹은 실습 전용으로 새로 만드는 것을 권합니다.
- **API 허용 IP 목록**: 내 공인 출구 IP가 필요합니다. 아래처럼 직접 조회하세요.

```bash
curl -s https://api.ipify.org
```

이 값이 AKS API 서버에 접근할 수 있는 유일한 주소가 됩니다. 조회된 IP를 입력표에 `<IP>/32` 형식으로 기록하세요.

> [!NOTE]
> 위 명령은 외부 서비스를 호출해 "인터넷에서 보이는 내 IP"를 알려줍니다. VPN을 켜고 끄거나 네트워크를 바꾸면 이 값이 달라지므로, **Lab 05에서 접속이 안 되면 가장 먼저 다시 확인할 값**입니다.

- **CIDR, VM SKU, 노드 수**: 아직 비워둡니다. Lab 02에서 쿼터와 용량을 확인한 뒤 결정합니다.
- 비밀번호, 토큰, kubeconfig 내용은 이 표에 절대 적지 않습니다.

> [!WARNING]
> 확실하지 않은 값을 **추측해서 채우지 마세요.** 빈 값을 임의로 채우면 이후 모든 프롬프트가 잘못된 전제를 사용하게 됩니다. 모르겠으면 "이 값은 어떻게 확인하나요?"를 에이전트에게 먼저 물어보세요.

## Step 3. 내 Azure 범위를 읽기 전용으로 확인하기 (15분)

**사용 Skill:** `azure-resource-lookup`

아래 프롬프트를 복사해서 실행하세요. `[resource-group]`은 입력표의 값으로 바꿉니다.

```text
azure-resource-lookup을 사용해 내 scope의 [resource-group]과 필요한 기존 foundation 자원을 읽기 전용으로 확인해줘. 리소스를 생성, 변경, 삭제하지 말고 접근 불가 항목은 권한 부족으로 구분해줘.
```

**예상 결과:** 에이전트가 실제 구독/리소스 그룹 정보와 기존 자원 목록(있다면)을 보여줍니다. 접근이 안 되는 항목은 "권한 없음"으로 명확히 구분해서 알려줘야 합니다.

**당신이 확인할 것**
- 실제로 조회된 구독, 리소스 그룹, 리전이 입력표와 정확히 같은가요?
- 리소스 그룹이 아직 없다면, 이 Lab에서는 **만들지 않고** 이름만 확정해 둡니다. 실제 생성은 Lab 05의 배포 단계에서 함께 진행합니다.
- 그룹에 이미 다른 리소스가 있다면, Lab 08에서 실수로 지우지 않도록 지금 목록을 기록해 두세요.

## 🚧 문제가 생겼다면

| 증상 | 원인일 가능성 | 해야 할 일 |
| --- | --- | --- |
| 조회 결과가 입력표와 다르다 | 구독 선택 오류 또는 오타 | `az account show`로 현재 구독을 확인하고 입력표를 정정 |
| 구독이 여러 개라 헷갈린다 | 기본 구독이 다른 것으로 설정됨 | `az account list -o table`로 확인 후 `az account set --subscription <id>` |
| "권한이 없습니다" 오류 | 해당 scope에 대한 권한 부족 | 내가 권한을 가진 다른 구독·리소스 그룹으로 진행 (권한을 스스로 올리려 하지 말 것) |
| Skill이 리소스를 만들려고 한다 | 프롬프트가 모호했음 | "읽기 전용"이라는 문구를 다시 강조해서 재요청 |
