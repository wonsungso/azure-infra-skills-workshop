- AKS를 만들기 전에 결정해야 하는 것들(운영 모드, 네트워크, 노드풀, 접근 제어)
- Skill의 도움을 받아 "누가 무엇을 할 수 있는지" 최소 권한으로 정리하는 방법

> 🎬 **미션 진행 상황**
> 내 권한과 범위는 확인했습니다. 이제 **"무엇을 만들 것인가"**를 결정합니다. 여기서 잘못 정하면 나중에 클러스터를 **처음부터 다시 만들어야** 합니다.

## 왜 이 랩이 필요한가요?

AKS는 한 번 만들고 나면 바꾸기 어려운 설정(네트워크 플러그인, CIDR 등)이 많습니다. 그래서 "만들기 전에" `azure-kubernetes` Skill로 Day-0 결정을 검토하고, `azure-rbac` Skill로 "누가 무엇을 할 수 있는지"를 미리 표로 정리합니다. 이 랩은 아직 아무것도 만들지 않는 **설계 단계**입니다.

## 시작 전에 확인하세요

- [Lab 01](01-orientation-and-setup.md)에서 scope 확인을 마쳤나요?
- 공통 입력표에 구독, 리소스 그룹, 내 공인 출구 IP가 채워져 있나요?

## Step 1. 내 구독의 쿼터와 용량 확인하기 (10분)

**사용 Skill:** `azure-quotas`

노드를 3대 만들려면 vCPU 쿼터가 그만큼 남아 있어야 합니다. 배포가 실패하는 가장 흔한 이유 중 하나가 쿼터 부족인데, **배포 직전이 아니라 지금** 확인하면 30분을 아낄 수 있습니다.

```text
azure-quotas를 사용해 내 구독에서 [region] 리전의 Standard DSv5 family vCPU 쿼터와 현재 사용량을 확인해줘. AKS 노드 3대(Standard_D4s_v5 2대 + Standard_D2s_v5 1대)를 만들 수 있는지 판단해줘. 변경은 하지 마.
```

**당신이 확인할 것**
- 필요한 vCPU(위 구성 기준 10 vCPU)보다 여유가 충분한가요?
- 부족하다면 리전을 바꾸거나 노드 수·SKU를 줄이는 것을 지금 결정하세요.
- 결정한 리전, SKU, 노드 수를 [입력표](../../templates/team-inputs.md)에 기록합니다.

> [!TIP]
> 여기서 확인한 **실제 조회 결과**가 이후 Skill 프롬프트의 근거가 됩니다. 쿼터를 확인하지 않고 SKU를 정하면, Skill은 그 값이 맞는지 알 방법이 없습니다.

## Step 2. AKS Day-0 결정 검토하기 (20분)

**사용 Skill:** `azure-kubernetes`

```text
azure-kubernetes를 사용해 [aks-name] 교육용 AKS의 Day-0 선택을 검토해줘. Standard 운영 모드, system/user pool 분리, Azure CNI Overlay + Cilium, load balancer egress, public API authorized IP ranges를 기준으로 대안과 위험을 표로 정리해줘. 리소스 변경은 하지 마.
```

**이 단계에서 사람이 판단할 것**
- system pool 2개 + user pool 1개 구성이 교육 목적에 맞는지 (운영 환경의 고가용성 구성이 아님을 이해)
- Pod CIDR, Service CIDR, DNS 서비스 IP가 서로 겹치지 않는지
- API 서버를 공개하되 허용 IP 목록으로만 제한한다는 것의 의미

> [!TIP]
> Step 1에서 확인한 쿼터 결과를 프롬프트에 함께 넣으세요. Skill은 내 구독의 실제 용량을 추측하지 않습니다.

> [!WARNING]
> "허용 IP 목록을 넓히거나 없애면 더 쉽지 않을까?"라는 제안이 나오면 승인하지 않습니다. 이 워크샵은 공개 API + 허용 IP 제한을 기본 보안 경계로 삼습니다.

## Step 3. 최소 권한 매트릭스 만들기 (15분)

**사용 Skill:** `azure-rbac`

```text
azure-rbac을 사용해 이 교육용 AKS의 최소 권한 매트릭스를 작성해줘. Azure 리소스 배포자, 역할 할당자, AKS control-plane managed identity, lab namespace 사용자를 분리하고 scope와 필요한 작업을 표로 보여줘. 권한을 변경하지 마.
```

**왜 역할을 이렇게 나누나요?** "리소스 그룹을 만들 수 있는 권한"과 "다른 사람에게 역할을 부여할 수 있는 권한"은 다릅니다. 그리고 "Azure 리소스를 배포할 수 있는 권한"과 "Kubernetes 안에서 Pod를 만들 수 있는 권한"도 완전히 다른 시스템입니다. 이 표를 만들어 두면 나중에 "왜 안 되지?"라는 질문에 바로 답할 수 있습니다.

> [!NOTE]
> 이 실습에서는 여러분이 클러스터를 만드는 사람이자 사용하는 사람입니다. 그래도 역할을 **나눠서 설계하는 이유**는, 실제 팀에서는 이 둘이 다른 사람이기 때문입니다. 지금 만든 표는 Lab 08의 인계 문서에 그대로 들어갑니다.

**당신이 확인할 것**
- 나에게 구독 Owner나 cluster-admin을 부여하는 제안이 없는지
- 이 랩에서는 권한을 **실제로 변경하지 않고** 표만 만든다는 것을 이해했는지

## ✅ 완료 체크리스트

- [ ] 쿼터를 실제로 조회해 리전·SKU·노드 수를 결정했다
- [ ] Day-0 결정표(네트워크/노드풀/접근)를 스스로 설명할 수 있다
- [ ] 결정한 값을 모두 입력표에 기록했다
- [ ] 최소 권한 매트릭스를 증거 로그에 연결했다
- [ ] 아직 Azure에 아무것도 생성하지 않았다

## 🚧 문제가 생겼다면

| 증상 | 원인일 가능성 | 해야 할 일 |
| --- | --- | --- |
| vCPU 쿼터가 부족하다 | 구독 기본 한도 또는 다른 리소스가 사용 중 | 노드 수·SKU를 줄이거나 다른 리전 선택 (쿼터 증설은 승인에 시간이 걸림) |
| CIDR 겹침 경고 | 기존 네트워크 또는 다른 참가자와 재사용 | 겹치지 않는 대역으로 직접 변경 (예: `10.244.0.0/16` → `10.245.0.0/16`) |
| SKU를 Skill이 추측함 | 쿼터 조회 결과를 프롬프트에 안 넣음 | Step 1 결과를 붙여넣고 재요청 |
| 권한 매트릭스에 Owner/cluster-admin이 등장 | 프롬프트 누락 또는 잘못된 제안 | 최소 권한 원칙을 다시 언급하며 재요청 |
